# Commercial reference analysis: Infineon CAPSENSE

**Institution:** Vers3Dynamics. **Principal investigator:** Christopher Woodyard.
**Audit date:** 2026-10-11. **Reference:** Infineon/capsense commit
`36580294e1587b2df8193f254f7e9b9b4aa6dd13`; inspected implementation files identify middleware version 11.0.0.

This is a source and public-interface audit, not a hardware experiment, a binary investigation, or a performance comparison. It informs the independent TRIAD electrostatic experiment. CAPSENSE is a configurable embedded sensing middleware with hardware-specific acquisition, calibration, digital processing, widget state, centroid estimation, position filtering, and diagnostics. Its application and measurement conditions differ from TRIAD's idealized four-electrode inverse problem.

## Provenance and licensing boundary

The published [LICENSE](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/LICENSE) was read before source inspection. It is a proprietary EULA, not an open-source license. Section 2 scopes source modification and compilation to specified uses involving Infineon hardware and limits distribution; Section 4 restricts derivative works, source reproduction, and reverse engineering, subject to its stated applicable-law exception. Public availability does not remove these restrictions.

The user subsequently reported permission from the author for an implementation in Rust and instructed that the entire TRIAD prototype use Rust. That is recorded as **user-reported permission**, separately from the published license; the audit has not verified a permission document, its scope, or the identity/authority of the grantor. No restricted implementation is copied into TRIAD, no line-by-line port is created by this audit, and no CAPSENSE archive is disassembled or decompiled. Any future code port would require the permission's scope and language constraint to govern that separate work. TRIAD's Rust physical model and scientific estimator are independently authored mathematical implementations.

Source and header inspection copies were kept outside the TRIAD repository in a reference cache. This report contains original summaries, public symbol identifiers, and source links rather than vendor implementation code. REA availability and actual invocation evidence are recorded separately in [rea-capability-audit.md](rea-capability-audit.md). No REA analysis of CAPSENSE is claimed.

## Evidence levels and inspected material

## Processing architecture

The README describes self-capacitance CSD, mutual-capacitance CSX, and inductive ISX, with buttons, matrices, sliders, touchpads, proximity, and other widget types. This is broader than capacitive localization alone. `Cy_CapSense_Init` initializes common and widget contexts and marks widgets enabled and working. `Cy_CapSense_Enable` performs configured startup activities; acquisition and calibration dispatch by hardware generation. Generic scan APIs initiate nonblocking scans; `Cy_CapSense_IsBusy` reads the common busy mask; the interrupt handler advances the scan and invokes configured callbacks. These are lifecycle mechanisms, not posterior uncertainty calculations. [Initialization source](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_control.c#L144), [scan/status source](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_sensing.c#L251).

`Cy_CapSense_ProcessWidget` checks widget ID, enabled status and some unsupported configuration combinations, performs enabled preprocessing/deconvolution, processes raw counts, then dispatches widget-status processing by sensing method. `Cy_CapSense_DpProcessWidgetRawCounts` visibly orders the common-mode library call, enabled raw filtering, supported SmartSense noise-envelope and threshold updates, baseline update, then difference calculation. Multi-frequency processing can follow. Liquid widgets and low-power/ALP configurations have explicit exceptions. The public processing wrapper aggregates error status; applications must use the API according to scan timing and return-status requirements. [Control dispatch](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_control.c#L711), [raw processing](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L487).

## 1. Baseline initialization and adaptive tracking

**Observed source:** `Cy_CapSense_FtInitializeBaseline` in `cy_capsense_filter.c` takes a mutable sensor context containing the current integer raw count. It assigns that count as baseline, clears fractional baseline storage, and resets the negative-baseline counter. Higher-level `InitializeSensorBaseline`, `InitializeWidgetBaseline`, and `InitializeAllBaselines` visit configured sensor/frequency contexts; baseline-inverse duplication is initialized when the relevant BIST guards are enabled. Outputs are context mutation and, in the wrappers, a status code. [Initialization](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L539).

`Cy_CapSense_FtUpdateBaseline` takes widget thresholds/coefficient, sensor raw count and baseline history, the inverse-baseline storage, and common configuration. It first checks enabled integrity duplication. When the negative-reset condition does not apply, tracking runs if sensor auto-reset is enabled or raw count is at most baseline plus the positive noise threshold. The mathematical interpretation is a gated first-order IIR update: a fixed-point baseline history is smoothed with current raw counts using weight `bslnCoeff/256`. Integer and eight fractional bits persist in `bsln` and `bslnExt`. The helper computes the weighted sum with division by 256 using an integer shift; fractional retention is visible, not an assumed floating-point filter. [Tracking](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L344), [IIR primitive](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L1103).

**State and parameters:** `bsln`, `bslnExt`, `negBslnRstCnt`, optional `ptrBslnInv`; `bslnCoeff`, `noiseTh`, `nNoiseTh`, `lowBslnRst`, and `swSensorAutoResetEn`. Fixed-point shifts are 8; the IIR normalizer is 256. Generated configuration supplies operational values; this audit does not invent universal defaults. The structure documents `bslnCoeff` as an eight-bit value, with smaller values producing stronger smoothing.

**Conditions and limits:** Tracking is designed to separate slow changes from positive touch excursions using thresholds. Its performance depends on scan period, thresholds and auto-reset policy. Startup initialization uses the measured raw count, so its interpretation depends on the physical state during initialization. The code contains no universally valid guarantee that baseline tracking distinguishes a long-lasting target from environment. This is an information and tuning dependency, not a measured product defect.

## 2. Baseline reset and drift handling

**Observed source:** In the same update function, if baseline exceeds raw count plus `nNoiseTh`, a counter increments unless it has already reached `lowBslnRst`, in which case baseline is reinitialized to raw count. The counter clears when raw is greater than or equal to baseline. Positive excursions beyond the positive threshold freeze tracking unless auto-reset is enabled. Output is updated baseline/counter/inverse duplication or an integrity error. Persistent history and parameters are those above. [Reset logic](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L357).

**Important distinction:** The header describes a number of below-negative-threshold samples; the body checks the old counter before incrementing and does not clear it merely because raw rises into the sub-baseline threshold band. Therefore, exact reset timing must follow the body and is not safely summarized as a strict consecutive-sample rule. No runtime consequence was measured. The reset counter is an eight-bit sensor field whereas `lowBslnRst` is a wider configurable field; valid generated configurations and effective range were not experimentally checked.

Hardware calibration is separate: `Cy_CapSense_CalibrateAllWidgets`, `CalibrateWidget`, and `CalibrateAllSlots` dispatch to generation-specific acquisition calibration. Documentation describes selection of CapDAC/IDAC values toward configured raw-count targets and return flags for calibration failures. This audit read generic dispatch and documented contracts, not every hardware calibration implementation. Mathematical interpretation: operating-point tuning of a count-conversion system, distinct from software baseline tracking and from TRIAD estimating environmental nuisance variables. Calibration targets, acceptable errors, and per-widget calibration state are configurable. [Calibration dispatch](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_sensing.c#L703), [slot calibration documentation](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_sensing.c#L738).

## 3. Raw-count filtering

**Observed source:** `Cy_CapSense_FtRunEnabledFiltersInternal` takes widget flags/coefficient, mutable sensor raw count, and history pointers. When ALP is selected it calls the library ALP path; otherwise enabled median, IIR, and moving-average operations run in that order. Each operation overwrites the count for the next stage. `Cy_CapSense_RunMedianInternal` and `FtMedian` implement a three-sample median with two previous input values. `RunIIRInternal` uses the same weighted IIR primitive with coefficient `iirCoeff`; performance mode preserves eight fractional bits in an additional low-byte history. `RunAverageInternal` averages the current input with one or three prior inputs, yielding lengths 2 or 4 with integer division. Initializers seed history with the current raw count. [Filter dispatch](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L978), [median](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L873), [IIR](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L800), [average](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L936).

**State and parameters:** Per-sensor and per-frequency raw filter histories, optional fractional histories; build flags, `rawFilterConfig`, `iirCoeff`, filter length/mode masks. Parameters and histories are not a posterior distribution. Filtering changes latency and temporal dependence; neither rejection reliability nor the correct tradeoff can be inferred from these operations alone. `Cy_CapSense_RunMfsFiltering` visibly combines multi-frequency differences through the median primitive where enabled; hardware frequency selection and disturbance rejection performance remain configuration-dependent.

**Documented ALP interface:** `Cy_CapSense_AlpRun_Lib` receives opaque ALP history, configuration, mutable raw count, and baseline. The source maps ALP on/off thresholds, proximity threshold, positive/negative noise thresholds, hysteresis, filter coefficient, and mode into its configuration. Exact recurrences and state meanings remain unavailable in readable source inspected here. ALP is not independently reproduced.

## 4. Adaptive thresholds

**Observed wrapper, documented inner algorithm:** `Cy_CapSense_DpUpdateThresholds` in `cy_capsense_processing.c` creates a threshold object and calls `Cy_CapSense_UpdateThresholds_Lib` with per-sensor noise-envelope state, current finger threshold, `sigPFC`, and a sensor-index/start flag. It writes returned finger threshold, positive noise threshold, negative noise threshold, and hysteresis into the widget context. Threshold state persists across calls; the library envelope also persists. [Wrapper](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L971), [contract](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_lib.h#L619).

**Update conditions:** Full SmartSense and appropriate CSD/ISX active modes must be enabled; raw processing excludes specified liquid/low-power widgets and ALP mode. The widget loop calls the noise-envelope update then threshold wrapper for each eligible sensor. A proximity widget copies the returned finger threshold to `proxTh` and scales the touch threshold by `proxTouchCoeff/100`.

**Interpretation and unknowns:** Noise-aware detection thresholds are established industrial concepts present in this reference. `sigPFC` is documented as a touch-sensitivity signal scale; a structure comment associates it with 75% of the configured signal-per-finger-capacitance quantity. The hidden library's threshold formula, aggregation across sensors, clamps, convergence, statistical coverage, and response to distribution shifts are unverified. The threshold object has a 16-bit finger threshold and eight-bit noise/hysteresis members. Those types are evidence, not proof of a probabilistic noise model.

## 5. Noise-envelope processing

**Documented interface, observed calls:** `Cy_CapSense_InitializeNoiseEnvelope_Lib` and `Cy_CapSense_RunNoiseEnvelope_Lib` receive a 16-bit raw count, sensitivity `sigPFC`, and mutable per-sensor noise-envelope object. The initializer is invoked from `Cy_CapSense_InitializeWidgetFilter` under applicable SmartSense guards. The running update is invoked after raw filtering and before baseline update in eligible raw-processing paths. Output is mutation of the envelope state and downstream thresholds. [Initialization call](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L731), [interfaces](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_lib.h#L645).

**State and unknowns:** The published object has five 16-bit fields and two eight-bit fields named generically `param0` through `param6`. Their documented generic descriptions do not establish meanings. An envelope-based noise estimate is the intended behavior; its recurrence, time constants, robustification, exclusion of touches, constants, and statistical interpretation remain unknown. It must not be equated with posterior localization uncertainty, and absence of an exposed uncertainty field does not establish absence of internal uncertainty handling.

## 6. Common-mode noise handling and difference calculation

**Observed dispatch, documented library:** `Cy_CapSense_CommonModeFilter_Lib` takes `cmfThreshold`, sensor count, and mutable sensor-context storage. Raw processing invokes it if the common-mode feature and widget flag are enabled. Its contract says it processes all sensors in a widget. The supplied context pointer is cast to a 16-bit pointer; the interface comment describes a 10-byte sensor structure. That ABI description is a contract, not a measured archive layout. [Call](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L516), [interface](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_lib.h#L711).

**Unknown:** Whether the common component is estimated by a mean, median, other rule, or stateful adaptive model; which fields are internally modified; exact threshold semantics and preservation of broad targets. No recurrence or performance assumption is substituted for the missing body. The wrapper has no explicit separate common-mode history parameter; this alone does not establish a stateless implementation.

**Readable downstream behavior:** `Cy_CapSense_DpUpdateDifferencesCmf` sets difference to the positive part of raw minus baseline. The non-CMF `Cy_CapSense_DpUpdateDifferences` sets difference to zero unless raw exceeds baseline plus `noiseTh`; when it passes that gate it stores the full raw-minus-baseline difference. Its prose mentions subtraction of the noise threshold, but the actual body does not perform that subtraction. Centroid stages separately subtract `calcTh` in their local windows. This is recorded to avoid mistaking documentation for actual source behavior. Persistent output is the sensor `diff`; input units remain raw counts, not SI capacitance. [Difference bodies](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L1009).

## 7. Proximity detection

**Observed source:** `Cy_CapSense_DpProcessProximity` takes widget configuration and context, traverses two status tests per sensor, and updates proximity and touch bits independently. Each test uses `proxTh` or `fingerTh`, with state-dependent hysteresis and its own debounce counter. The widget active mask summarizes active detections. Inputs are filtered/baseline-subtracted differences, existing state and thresholds; outputs are sensor bits, widget active bit, and counters. [Proximity source](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L1404).

**Math and state:** A two-state detector changes its switching level depending on the prior state. It confirms sustained above-threshold input through an integer counter. State consists of status bits and two counters per sensor initialized using `onDebounce`. Configurable parameters are `proxTh`, `fingerTh`, `hysteresis`, and `onDebounce`; SmartSense can adapt relevant thresholds as described above. The contract expects one call per newly scanned widget. Repeated calls on unchanged observations would advance counters, so call cadence is part of behavior. This reports detection categories, not a calibrated metric distance to a target.

## 8. Hysteresis, debounce, and position filtering

**Observed source:** `Cy_CapSense_DpProcessButton` uses threshold plus hysteresis for an inactive sensor and threshold minus hysteresis for an active sensor. A positive counter decrements each call; an at-or-below-threshold sample resets the counter and clears status; zero counter confirms activity. `InitializeWidgetStatus` initializes debounce arrays; documented `onDebounce` values 1 to 255 correspond to confirmation over consecutive detections. The source implements immediate clearing at the lower threshold for this path; it should not be described as a symmetric on/off debounce. Proximity repeats this independently for two states; sliders and touchpads have related widget/touch-specific logic. [Button](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L1311), [state initialization](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_processing.c#L168).

`Cy_CapSense_RunPositionFilters` takes X/Y position plus histories and runs enabled median, conventional IIR, library adaptive IIR, two-sample average, then jitter filtering. It mutates the output coordinates and history. The jitter primitive moves the current input one position unit toward the previous output, or leaves an equal input unchanged. `InitPositionFilters` initializes histories at first touch; CSX touch records match histories by touch ID. Radial processing has additional wrap handling. [Position filter](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L2456), [jitter](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L1129).

**Documented adaptive interface:** `Cy_CapSense_AdaptiveFilterInitialize_Lib` and `AdaptiveFilterRun_Lib` receive coefficient bounds (`maxK`, `minK`), movement thresholds (`noMovTh`, `littleMovTh`, `largeMovTh`), divisor, and position history; the run call mutates current X/Y. The contract requires first-touch history initialization externally. Its exact adaptive law, constants beyond configuration fields, and predictive/statistical meaning are unknown. Temporal stabilization does not establish inference-time error-probability calibration.

## 9. Slider and touchpad position estimation

**Readable legacy slider:** `Cy_CapSense_DpCentroidLinear`'s three-sensor branch finds a maximum, resolves equal maxima using a local three-sensor sum, and computes a weighted interpolation from the maximum and its immediate neighbors. Local strengths are positive raw-minus-baseline values after `calcTh` removal. Interpretation: center sensor index plus a neighbor imbalance divided by total strength, scaled to widget resolution. `centroidConfig` selects normalization by sensor count or count minus one, with an optional half-cell offset. Empty sum yields no position. Eight-bit scaling and rounding offset `0x7F` are explicit. The legacy branch has a placeholder for more-than-one centroid rather than a verified multi-touch estimator. `DpCentroidRadial` uses analogous interpolation with wrapped neighbors and position normalization; `DpCentroidDiplex` uses mapped slider information. [Legacy linear](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L726), [radial](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L837).

**Readable advanced slider:** The same file contains source bodies for `Cy_Capsense_SliderPeakDetect`, `SliderDetectTouchZone`, `SliderCalculatePositionNormalFinger`, and `SliderCalculatePositionFatFinger`. They must not be confused with the binary-only advanced touchpad routine. Peak detection tests local maxima above hysteretic touch threshold, bounded by supported touch count. Zone grouping compares neighboring differences against peak strength times `fingerSigThMult/256`. The normal-finger routine forms a five-sensor thresholded window, uses fixed-point weights corresponding to offsets around the peak, and configurable inner/outer edge corrections; it guards the central denominator term and clamps output to resolution. The fat-finger routine uses a weighted average across the detected zone with half-cell normalization. The parent branch classifies width relative to normal/fat/large-object thresholds, applies size hysteresis, can suppress a latched large object, tracks touch IDs and preserves position-filter histories. [Peak/zone](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L2886), [five-sensor position](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L3136), [zone position](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L3276).

**Readable touchpads:** `Cy_CapSense_DpCentroidTouchpad` separately applies a three-sensor interpolation to column and row axes for its one-centroid branch; either missing valid axis produces no position. `Cy_CapSense_DpFindLocalMaxDd` locates CSX peaks, and `DpCalcTouchPadCentroid` computes local 3-by-3 weighted X/Y sums with thresholded strengths, zero padding at edges, configured scaling, and integer rounding. It stores a strength-like Z derived by division by 16 and saturation at 255, not a calibrated uncertainty. `DpTouchTracking` uses prior peaks and distance matching, including a Hungarian assignment routine in the readable file; touch age/debounce and maximum reported touch count affect reported records. [Axis estimator](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L955), [CSX centroid](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L1402), [tracking](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L1571).

**State and parameters:** Raw/baseline/difference sensor arrays, widget active/finger-type flags, prior touch records/IDs/age, filter histories; sensor row/column counts, resolution, `calcTh`, centroid flags/count limits, peak/size thresholds, hysteresis, edge offsets, and tracking configuration. These are geometry-specific signal estimators; their assumptions do not establish uniqueness for an arbitrary unknown-permittivity target. No localization errors or failures were measured on actual hardware.

**Binary-only advanced touchpad:** `Cy_CapSense_DpAdvancedCentroidTouchpad` builds `cy_stc_capsense_advanced_centroid_config_t` and passes a buffer of sensor **differences** to `Cy_CapSense_AdvancedCentroidGetTouchCoordinates_Lib`, despite the latter's public comment calling the array raw counts. Configuration includes finger/penultimate/virtual-sensor/cross-coupling thresholds, resolutions, sensor counts, edge correction, and two-finger enable. The interface describes up to two fingers. Source proves the wrapper and input preparation; the inner coordinate formula and ambiguity rules remain unknown. [Wrapper](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_centroid.c#L1177), [library contract](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_lib.h#L442).

## 10. Sensor validity and fault handling

**Observed source:** `Cy_CapSense_CheckBaselineInv` compares the baseline to stored inverse duplication when BIST and baseline-integrity guards are enabled. A mismatch returns bad data, clears widget working, and sets a baseline-integrity result bit; tracking is skipped. Initialization and successful updates maintain that duplication. This checks integrity of stored data, not physical localization correctness. `ProcessWidget` checks IDs and enabled/configuration states; `IsBusy` reports scan state. [Integrity body](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_filter.c#L277).

**Documented and source-dispatched diagnostics:** Generic `Cy_CapSense_RunSelfTest`, `CheckCRCWidget`, `CheckIntegritySensorBaseline`, `CheckIntegritySensorRawcount`, and `CheckIntegritySensorPins` dispatch to fourth/fifth-generation variants. Inputs include widget/sensor IDs, optional numeric lower/upper count limits, test masks, and mutable context. Contracts cover RAM CRC, raw/baseline range/integrity, pin shorts, capacitance/voltage checks, unavailable features and busy/error/fail status. `RunSelfTest` explicitly excludes raw-count and baseline integrity tests, which use their specific APIs. Per-generation detailed test bodies were not exhaustively audited. State includes BIST result/context and widget status; configuration/build guards select availability. [Generic self tests](https://github.com/Infineon/capsense/blob/36580294e1587b2df8193f254f7e9b9b4aa6dd13/cy_capsense_selftest.c#L57).

**Limits and unknowns:** Existence of checks is not evidence that a deployed product schedules them or refuses all physically ambiguous measurements. Conversely, no unexposed internal behavior is assumed absent. This audit has no firmware image, actual generated configuration, executable comparison, sensor hardware or environmental test results.

## Lessons and unanswered questions for TRIAD

Adaptive baselines, noise-aware detection thresholds, configurable raw/position filters, common-mode processing interfaces, hysteresis, debounce, peak grouping, large-object classification, touch tracking, and status/integrity checks already exist in this established reference. TRIAD must not present those general concepts as novel. A noise envelope is a noise-related state; a centroid amplitude, detected-object category, or working status is not automatically a posterior error probability.

TRIAD can independently test information limitations using a specified physical forward model, an unknown dielectric nuisance variable, covariance-aware likelihoods, and held-out environmental sequences. Any future observability criterion must be evaluated against posterior expected localization error with the same data and information budget. Local sensitivity need not imply global uniqueness; temporal compensation requires identifiable calibration information. These are research design lessons, not replicas of vendor algorithms.

This audit does not establish whether CAPSENSE internally computes any uncertainty quantity, how its binary-only methods treat ambiguous signals, or how commercial systems behave under TRIAD's artificial drift. It does not establish a commercial defect, superiority of TRIAD, or scientific novelty. The proposed research question remains open until independently specified selective-prediction experiments are run. A fair commercial comparison additionally needs authorized executable/hardware measurements with meaningfully comparable geometry, sensing conditions, calibration, timing and outputs.
